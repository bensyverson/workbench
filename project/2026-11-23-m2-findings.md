## The tolerance

`GLSL_TOLERANCE = 1e-3` per color component, in `kit/harness/tolerance.js`.

| Fact | Figure |
|---|---|
| Worst standard case | 2.19e-4: headroom 4.6x |
| Stress case | 5.18e-3: 5.2x over the tolerance, about 1.3 steps of 8-bit color (1/255 = 3.9e-3) |
| A fault of 5e-4 | escapes GLSL (below), is caught by the exact JS pair |
| A fault of 1e-3 or more | caught in both backends |

**One figure or two?** Two options. (a) One declared figure, 1e-3. (b) Two: 1e-3 for typical use and a looser one (the prerelease test already holds the stress case to 1e-2, only to catch a blow-up) for the corners.

**Recommendation for Ben: (a), one figure on the target, with a per-case override that names its reason.** The reasons: the sensitivity result above was measured against 1e-3, and every loosening buys escapes (a 5e-3 figure would also miss the 4e-3 nudge, `grid-red-large`, that 1e-3 catches); a second declared figure becomes the one authors reach for; and the stress overshoot is a property of one sketch's amplification (five-octave noise chained twice, at `k` 8), not of the target, so it belongs to a case that says so ("domain-warp at its corners: 1e-2, because...") and so announces itself, as tolerance should. This is a ruling the evidence does not force: the stress cause is unknown, and if it turns out to be fused multiply-add on this one GPU, the right figure may differ elsewhere. Today the prerelease test's 1e-2 is already a de facto second figure with no declared reason; (a) with an override makes it explicit.

Three further points. The figure is one GPU's, so 4.6x is the only allowance for other renderers. It belongs to the GLSL target (the fields Dialect's `targets.glsl.compare` says only `"tolerance"`) and sits in the harness only because the target was another leaf's. And the draft's other open question, whether image-level checks (mean absolute error between interpreter and GPU PNGs, with `peep`) should join the harness, was offered earlier in the session (this leaf's note) and is **also for Ben**; nothing was built.

### Every change beyond the planned value types, and why

From the leaves' notes (gmyAFW, 4RDskO, zwqdaX, tXOjGg, ZDCBUt, lH5oTo, ijlr3x, psq9tb) and confirmed against the file list above. Each is marked **D** (M1 had a DMG assumption in a place that should be neutral, now moved to the Dialect or generalized), **C** (a flaw in the core exposed, not DMG-specific), or **N** (new need of shaders that the core now carries).

1. **The default number type, `Environment.numberType` (D).** M1 gave every untyped literal, every `++`/`--`, every `for` counter and the verifier's counter the type `f64`, hard-wired in five lowering sites and one verifier rule. A shader wants f32 and a Game Boy target wants integers, so Ben ruled the default belongs to the Dialect (DMG f64, fields f32). It touched let, argument, ternary, array and object items, counters and `++`/`--`, but **no IR node**. The sharpest finding of M2 for H2: the neutral core needed this setting, and M1 had it as an unstated constant.
2. **Untyped literals are literal trees, and baked array and struct constants keep numbers untyped until used (D/N).** A bare-literal rule alone made `2 * 3 * k` an error; arrays and structs needed the same treatment, found by review 2 (item 5).
3. **The loop-bound rule accepted only a read-only load whose owner was `Grid` (D).** The verifier already accepted any read-only place, so lowering and the verifier disagreed, and a fields param could not bound a loop. Both now accept any read-only place. This **bakes in "read-only means a size"**, which is false for DMG's `w.frame`; DMG output is unchanged, the rule is looser than "declared size", and the explicit size flag is parked (job 6r597q's note; see "What M3 should change").

   > **Corrected (2026-11-24, job piyiFx):** the size flag is built, not parked. `Member.size` is declared by the Dialect (the DMG grid's rows and cols; a fields param with a `max` of at most 2^24 - 1) and read by lowering and the verifier; any other read-only place, `w.frame` among them, is L007. DMG's goldens and the survey are unchanged (no preset used such a bound). Until that fix, DMG accepted `for (i < w.frame)`.
4. **`++`/`--` and `for` counters follow the number type, and f32 counters are bounded to 2^24 (C).** f32 `i + 1` stops changing at 16,777,216, so the loop bound limit follows the counter's type. A review found `for (let i=0;i<20000000;i++)` lowered and never ended (review 2, item 1).
5. **Component assignment rebuilds the vector (N).** A vector has no places inside it, so `a.x = 1` lowers to a `set` of a `vec` node. This is lowering, not IR.
6. **A store to an f32 place needed a rule, `Coerce.type` gained `"f32"` (C).** Review 1 found it failed verification as "a kit bug". The store rules were integer-centric and f64.
7. **`sameType` compared JSON strings, so key order made two equal vector types different (C).** Now compared by sorted keys.
8. **`join` falls back to a union, and that fallback was silent for numbers (C).** `b ? k : 0.5` with an f32 and an f64, or two vector types, became a union that lowering and the verifier accepted. The rule exists for DMG's draw results (a sprite name, a partial record or null). The core now rejects a union holding an f32 or a vector, recursing into lists and structs (`mixesNumbers`). The highest-severity finding of M2.
9. **Non-finite and -0 literals (C).** `1e999` lowered to `num Infinity`, which the JSON form cannot hold; L016 now rejects it in lowering and the verifier's `num` rule rejects it itself. M1 never met this because no DMG program writes one.
10. **The verifier's `for` counter follows its start's type (D)**, and a Dialect declaring a writable member without an `effect` gets V007 (a rule M1's `read Owner.name` convention implied but did not state).
11. **Library and helper name collisions are an error; `lowerProgram` throws on duplicate helper or const names (C).** Last-wins was invisible in M1, where there was no Library.
12. **Environment additions: `vectors`, `conversions`, `componentAliases` (so `c.r` reads `c.x`), `FnSig.numeric` (a type variable limited to numbers or vectors) (N).** All optional. `FnSig.numeric` was the only new idea in a signature: generic `mix` and `length` are one intrinsic, not an overload set.
13. **`json.js` gained `jsonDifference` (N)** for the verifier's round-trip check; **`ir/index.js`** exports it and the verifier. **`lower/query.js` one line (C)**: `reduce` with an effectful initial value lost the effect; the verifier found a real M1 bug (lH5oTo).
14. **The JS backend, `emit.js` (N).** `emitKernel` takes an optional `{ intrinsics }` and returns `prelude: string[]` (empty for DMG, so DMG source is byte-identical); `expr` splits into rounding and raw forms; the scope type widened; locals that collide with `Math`, `Infinity`, `NaN`, `$`-names or an intrinsic name are renamed; a negative literal base of `pow` is parenthesized (`-2 ** 2` is a SyntaxError). The collision and `pow` fixes are bugs M1's emitter had but no DMG program could trigger.

**Counts by first-listed class**: of the 14 items, D 4 (1, 2, 3, 10), C 6 (4, 6, 7, 8, 9, 11) and N 4 (5, 12, 13, 14). The classes overlap and the split is my judgment.

**Found and not fixed**: a bare function call (`length(v)`) lowers with a `global` receiver named like the function, though `ir.d.ts` says a call's `fn` is a path with no receiver; the interpreter skips evaluating such a receiver (job ijlr3x's note). Neither file nor job records a fix; it is an inconsistency between the IR's type and its lowering.

### What was DMG-specific in the core

- **f64 as the only number** (item 1, 4, 10): five lowering sites and a verifier rule. Fixed by the Environment setting.
- **A loop bound is a `Grid` size** (item 3): replaced by "any read-only place", which was itself a guess; now a Dialect-declared `Member.size`.
- **The effects vocabulary.** The fields Dialect has **no effects at all**: a pixel is pure, and the only effects its Kernels record are calls to helpers. So the effect system, which M1 found the most useful part of the IR, **received no second test from shaders**: a definitional zero. What did change: "pure" had to read "no effect except calls to helpers", a backend deciding purity must look through them, and the verifier counts any load of a writable place as `read Owner.name` (item 10). Effects, rng, events and queries remain DMG-only.
- **Store rules.** The fields Dialect has no stores (uniforms are read-only), so the integer store rules (`u8`…`fix`) were not exercised by M2 beyond adding f32. The hostless integer backend that would exercise them (M5) is untested ground.
- **Unions**: `join`'s fallback (item 8). DMG needs unions; numbers must not use them.
- **Strings, optionals, entity references, lists with a maximum, struct payloads**: unused by fields (it has one enum-like choice param). They stayed in the core without harm and without a second user.

### What stayed neutral

- **`kit/parse` and the DMG Dialect: 0 lines changed.** Typed operators needed nothing in the parser, which accepts `uv + k * q` as JavaScript; D1 lives wholly in lowering's operator resolution.
- **Helpers, the call-site strict join and the Library lowered unchanged.** `pmod`, `vnoise` and `fbm`, written in the Runtime Subset, lower like DMG's helpers with parameter types from call sites, and reach both backends with no spelling.
- **The interpreter ran M1's Kernels unchanged**: the effectful DMG lambdas of 04–07 give original-equal traces, because loads, calls and stores default to plain property access on host objects.
- **The GLSL backend and its LIR needed no core change.**
- **`vec` is the only new Expr kind; `f32` and `f64` are the only new Ops** (`ir.d.ts`; `Type` gained `"f32"` and `VecType`).

### Verdict

**H2: supported for two Dialects, with the cost stated.** Games and shaders now share a typed IR, a verifier, a lowering, a JS backend and an interpreter; one new node kind, two new operators, one new Type and one new Environment field carry the second domain; the parser and the DMG Dialect did not move. Against that, the second Dialect forced changes to 14 of 26 existing source files, and five of the changes (1, 3, 4, 8, 10) removed assumptions M1 had made without saying so. That is H2's failure condition read strictly ("the kit has to change for the second dialect"), and read as intended it is the discovery working: every one of the 14 is a Dialect-neutral generalization, none is shader-specific logic in the core, and DMG's survey and goldens are bit-identical. Caveats: **only two Dialects** (the third, data tools, is M3's); the **effect system and store rules got no shader exercise**; the neutrality of the loop-bound rule is a guess; and the reviews (below) caught the three most serious flaws, which means the neutral core was achieved by review as much as by design.

## H3: do typed operators make shader code pleasant without confusing authors?

**Verdict: provisional. No sign of confusion; the test barely exercised the operators.** Ben ruled for typed operators (D1) before testing them; this is the check.

**Part A, the two sketches in two styles** ([comparison](2026-11-23-h3-styles-comparison.md)). The call style uses six intrinsics (`vadd`, `vsub`, `vmul`, `vdiv`, `vscale`, `vneg`), each the operator it names; scalars keep operators in both styles. Both styles of all three sketches lower, verify and agree on every f32 component of the recorded grids (`node --test kit/dialects/fields/test/calls.test.js`: 3 pass). Length, `node scripts/h3-styles/measure.js`: the call style is 3 to 6 percent longer in characters (swirl 643 / 665, bulge 592 / 621, domain-warp 1,235 / 1,303), 4 to 7 percent in tokens, the same number of lines, `domain-warp`'s longest line 108 / 142 characters and its deepest nesting 3 / 5. Readability is the author's reading, not a measurement: typed reads as the book's math (`p + k * q`), the call style reads inside out. The sketches use few vector operations, which is also why the cost is small.

**Part B, the fresh-agent round** ([results](2026-11-23-h3-trial-results.md), job vkQDxc). 10 fresh agents (3 Sonnet and 2 Haiku per style) wrote 3 sketches each from one documentation packet per style, checking with `scripts/h3-trial/check.js`:

| | typed | call |
|---|---|---|
| sketches written | 15 | 15 |
| valid on the first check | 14 of 15 | 15 of 15 |
| diagnostics | 2 (both L002, `u.TAU`) | 0 |
| from expecting plain-JS semantics | **0** | **0** |

(Counts from the results document; the logs live in a session scratchpad and are not in the repository, so the table cannot be re-run from the repo.)

**Why this is not a verdict.** Only 4 of the 15 typed sketches used an operator on two vectors; the others did scalar arithmetic on components, as the book does, and none of the 15 call-style sketches needed a vector function. Tasks solvable in scalar math do not test typed operators, so the result is "typed operators did not get in the way", not "authors reach for them and succeed". The L001 tip lists every callable name, including the call-style functions, in both styles, and operator-style L003 tips show operators to call-style agents, so the styles leaked into each other's diagnostics. Call style is a convention the Dialect does not enforce. Agents ran the default sample pixels only. One round, one task set.

**Open: the second round.** Tasks stated in vector terms (a point, a direction, a 2 × 2 rotation applied to a `vec2`, a mix of two `vec3`s), with inputs that tempt plain-JS habits (arrays of numbers, `Math.hypot` on a pair, comparing vectors with `===`), and per-style diagnostic tips first. The H3 verdict is "fails if authors or models keep expecting plain-JS behavior"; until that round runs, what is known is that they did not in 30 sketches that rarely needed to.

**What the highest-severity ones were.** (1) *Silent acceptance*: a ternary or inferred return mixing f32 with f64, or two vector types, became a union with no diagnostic (review 1, high); the verifier written as the safety net accepted it too, because it encoded the same permissive rule. (3) *An infinite loop that lowered clean*: an f32 counter bounded at 2^53 (review 2, medium).

**What it says about the process.**

- **Every review found something the author's own green tests did not.** Nothing built in M2 reached its commit clean of a review finding that mattered, and the findings fall, in my grouping, into: silent acceptance where the type system should have said no (4: review 1 #1, review 2 #1, #3, #7), semantic gaps between JS and GLSL (5: review 2 #8, review 3 #1, #2, #3, #8), name and identifier collisions (4: review 2 #2, review 3 #4, #5, #6), gaps in the core's type rules (3: review 1 #2, #3, #4), a documentation claim that overstated (1: review 2 #5, that a test compared the GLSL `ihash` with the reference when it was only checked by pattern), and three others (a loop-bound rule, a misleading diagnostic, an emitter syntax error). A reviewer probing with adversarial programs found all of them; tests written beside the code found none of these before review.
- **The verifier's first form was not a trustworthy kernel.** The guarantees note says the Lean-style lesson is a small trusted core; review 1 found the verifier agreeing with the lowering it was meant to check. The fix made it stricter than lowering in places, which is the direction the note wants.
- **The comparison harness came after the review that found the JS and GLSL divergences, and found none new**: the three sketches agree, and the planted faults show the harness's sensitivity (above). That is weak evidence for the review, since the sketches may not reach the divergent constructs (`%` on f32, NaN truthiness).
- **Unreviewed M2 code**, to the best of the notes I read: `kit/harness`, `kit/debugger`, the call-style intrinsics and the H3 kit, and the fix commits themselves (b7421ae, 0da8578). Verify against `project/agents/review.md` before the handoff; I found no review job for them.
- **Cost.** About 1,500 lines of production code were reviewed in review 1 (the M2 handoff's figure), and each review's findings were fixed in a leaf of their own.

## What M3 should change

- **The Definition API and a generic `.construct()`** (H4). The fields Dialect is hand-written data (`FIELDS_DIALECT`), a separate Environment function, a hand-written `field(name)` builder and `lowerField`; none of it came from `Dialect(…)` calls. Compare it with the proposal's §8.1 sketch (see the correction there): the sketch's builder is a design not yet tested. Two hand-written Dialects are a data point for what the generic form must express: types, a number type, Iteration Spaces, intrinsics with spellings and references, a Library, targets with a compare mode.
- **Combining and extending Dialects** ([the note](2026-11-23-dialect-composition-and-extension.md)). M2 gives it one piece of evidence: the Library as a shared lowering target worked with no change, which is option B's lowest layer. Its first next step, "measure how separable the DMG Dialect is from the core", is now partly answered: the kit's core changed in the 14 files above while the DMG Dialect itself changed in none, so the separation holds in one direction (the core did not need the DMG Dialect to move). The conservative-extension check (every base program lowers to identical IR) is exactly what the survey, the goldens and the 42-run diff already did for DMG; make it a named kit test.
- **Per-style diagnostic tips.** The L001 and L003 tips must name only the style the author is in, before the second H3 round and as a general rule: tips that name another style's operations are noise.
- ~~**A size flag on read-only places** (job 6r597q).~~ Built 2026-11-24 (job piyiFx). It was: replace "no store rule means a bound" in lowering and the verifier with a Member flag the Dialect declares. Un-park when a Dialect declares a read-only value that is not a size; M3's Definition API is the natural place.
- **A hostless DMG backend (M5).** M2 found the first stage of the LIR; integer stores, explicit wrap and clamp and the integer default number type are the untried half, and they are what the DMG's `u8`, `u16` and fixed-point stores would need. Until then, "H2: the core covers games" means "games run through a JS backend that leans on the host".
- **Range analysis.** The guarantees note names it as the first analysis to turn guarantees into diagnostics; M2 supplies two concrete first uses: a param that bounds a loop is unchecked (the fields README: a count param needs a `max` below 2^24), and an output color staying in [0, 1]. The backlog entry's un-park condition is met by the second use.
- **The loop-bound rule** (item 3) and the "pure means no effect but helpers" reading belong in the Definition API as declared properties, not inferences.
- ~~The fast suite's budget~~: withdrawn; it is 8.3 s alone (job qanJzB).
- **Tolerance's home**: move `GLSL_TOLERANCE` to the target and make `compare: "tolerance"` carry it, per the decision for Ben above.
- **The three-Dialect test of H2**: the third Dialect, data tools with a SQL plugin, is M3's done-when; it is the first to exercise effects and stores outside the DMG.
