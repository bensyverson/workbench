# M3: Kit v0, the plan

*2026-11-24. Imported into job under `8qHPT3` (the Workbench Kit) on 2026-11-24; after import the tracker is the plan, so change a leaf with `job edit`, not this file. Roadmap row: [proposal §15](2026-11-23-workbench-kit-proposal.md). ## Goal

M3 turns two hand-written Dialects into a kit that a fresh agent can build a third workbench on. It tests four hypotheses:

- **H4**: most fluent grammars can be declared as constructs and slots. Test: re-declare the DMG and fields Dialects through a generic Definition API, with identical IR and output.
- **H11**: Dialects can own their passes. Test: a fresh agent writes a correct domain pass against the query and pass API from the documentation alone.
- **H5**: a fresh agent can build a small workbench from about 8,000 tokens of kit documentation (`START.md`, `API.md`, `hello`).
- **H2**, finished: three Dialects, one of each kind (game, shader, data). The third is the first with effects and stores outside the DMG.

## Rulings that bind the plan (Ben, 2026-11-24)

- **Order:** the Definition API, then the query and pass API, then the docs, then the third Dialect's fresh-agent test.
- **H4's bar:** both DMG and fields are re-declared through the Definition API, and the M1 survey (126 / 111 / 7 / 4 / 4), the goldens, the differential run and the M2 harness figures are unchanged. This is the conservative-extension check made a named test.
- **Tolerance:** a target declares one compare figure (`compare: tolerance(1e-3)`), and a case may override it with a stated reason that the harness reports. `GLSL_TOLERANCE` moves out of `kit/harness/tolerance.js` to the GLSL target.
- **The third Dialect starts as Dream Code**, written by a subagent from Manuel's prompt with no kit knowledge (done: the file linked above). It is then converted to a Dialect, and to a Grammar once the Definition API's Grammar half exists.

## What the Dream Code asks of the kit

Read against what M1 and M2 built (this is my reading, not a ruling):

| The Dream Code needs | What the kit has | Gap |
|---|---|---|
| Runtime lambdas over a row and params (`row => row.units * row.price`, filters, derives) | The Runtime Subset, typed lowering, per-Program Environments (fields builds one from its params) | A `row` Iteration Space whose parameter type comes from a schema inferred at build time; string and date value types with typed operators (D1); an Environment built per program from table schemas |
| Typo errors with a "did you mean" and a fixit (`row.revnue`) | Diagnostics with codes, spans, tips; fixits in the parser | Proxy-style builder diagnostics in the Grammar half (the Grammar's generated builder, not lowering) |
| Build-time lambdas that see schemas and return grammar | Build-time lambdas are plain host JS in the Grammar (the proposal's `bake`) | A checked phase rule: a build-time lambda may not read a param (E-PHASE) |
| A program DAG of tables, params, charts, views; lineage and "what reruns when a param moves" | One typed IR for Kernels; queries are not built | The DAG is a second IR above the Kernels. Who owns it is a decision (leaf below) |
| A SQL plugin: SQL text, `${param}` as bound values, result schema inferred at build time, errors with spans inside the SQL | Nothing: every slot is JS | A slot whose body is another language, with its own parser, checker and a schema it hands back. Also an engine to run it: a dependency decision (leaf below) |
| Fragments adding methods and typed attributes to one component | Proposed in §8.2, not built | The Grammar half |
| An Environment an agent mutates through an event log, with permissions, undo and replay | The proposal's workflow (phase 3) only | The first stores and effects outside the DMG; the first use of "effects" for something that is not game state |
| Custom components with both lambda kinds (`cohort`) | Constructs and slots in the DMG Grammar, hand-written | Declaring a construct from core pieces: H4 proper |

## Order and reasons

1. **Design the Definition API from three data points** (DMG, fields, the Dream Code), before building it, so it is not fitted to two games-and-pixels examples. A design doc Ben reads.
2. **Build the Dialect half, then the Grammar half.** The Dialect half (types, number type, Iteration Spaces, intrinsics with spellings and references, a Library, targets with compare, the size flag, declared purity) comes first because the converted data-tools Dialect and the re-declared fields Dialect need only that. The Grammar half (constructs, slots, fragments, the generated builder) follows.
3. **Re-declare fields, then DMG.** Fields is the smaller test; DMG is the real one, with stores, effects and integer rules.
4. **Convert the Dream Code to a Dialect** as soon as the Dialect half exists, so the Definition API meets a third Dialect before it is frozen. Its Grammar waits for the Grammar half.
5. **The query and pass API**, once the Definition API is stable, since passes belong to a Dialect.
6. **Docs, then the fresh-agent runs** (H5, H11, H2): the last leaves, because they measure the documents.

## Open decisions (each is a `decision` leaf, to be settled with Ben when its turn nears)

- **Is the program DAG part of the kit core, or a Dialect's own structure?** Options: a small generic graph IR in the kit that Dialects instantiate (DMG's Game, the data program, a field's params), or each Dialect keeps its own. It decides what "lineage" and "downstream of a param" mean for the query API. Needs the design leaf's evidence first.
- **How the SQL plugin runs.** Options: a small hand-written SQL subset (parser, checker, executor), which avoids a dependency and gives spans and schema inference for free but is real work and will never be SQLite; or an embedded engine (sql.js, a wasm blob), which is a dependency and a large file in a one-page artifact, but runs real SQL. The project rule is to avoid dependencies and to ask before adding one.
- **What the fresh-agent test builds.** Options: the data-tools workbench again (cheap, but the converted version is then in the repo to be copied, so the agent must not see it), or a fourth domain the repo has not seen. Settle once the docs exist.
- **How a slot in another language (SQL) fits the Grammar:** a new slot kind, or a Dialect-supplied "foreign lambda" with a declared parser. Decide in the design leaf.
