# kit/run: the scheduler

Runs a composed workbench: kit/compose's composed record, each part stepped by its package's runtime ([kit/define](../define/README.md)'s `defineRuntime`), on one workbench time. The spec is [the clocks draft](../../project/2026-11-25-clocks-draft.md) as ruled 2026-11-26, and [the build record draft](../../project/2026-11-26-build-record-draft.md) for rebuilds. No Node built-ins; it runs in the page. Drawing a composed page on a canvas is [kit/page](../page/README.md)'s.

```js
import { createRun, createDriver, replay } from "kit/run";

const composed = composition.build({ packages, runtimes });          // S116 refuses an overflowing reliable queue
const run = createRun(composed, { runtimes, packages, seed: 1, inputs: [
  { kind: "in", T: 2.25, part: "level", name: "pad", value: { up: false, down: false, left: false, right: true } },  // a scripted D-pad: one record on the part's pad Event input
] });
run.runUntil(3);                     // headless: as fast as it can; frame parts at a nominal 60 Hz
run.state("fx");                     // a part's state now
replay(composed, { runtimes, packages }, run.record()).ok;           // same log, same hashes: true

const live = createRun(composed, { runtimes, frames: "display" });
const driver = createDriver(live);   // the page calls driver.frame(wallSeconds) once per display frame
```

## API

| Export | Does |
|---|---|
| `createRun(composed, options)` | compiles, clocks, keys and inits every part; throws `RunError` with N006 (a clock that is not one), N007 (a record kit/compose would not have built: a wire whose `overflow` is not `"keepLast"` or `"keepFirst"`, or a layer the record's own fields contradict, below) or S116 (an overflowing reliable queue), and a plain Error for a part with no runtime |
| `run.step()` | runs the next instant: `{ T: "19/8", stepped: ["level", "fx"] }`, after applying the inputs stamped before it, each at its stamp. When no part is due, it applies the log's inputs a stamp at a time until one restarts a part, and runs that part's first instant; when none does, it has applied the whole log, `run.T` is the last stamp, and it returns null (an input stamped before that stamp then throws, naming it) |
| `run.runUntil(t)` | runs every instant at or before `t` (seconds with a denominator up to a million, a rational `{ n, d }`, or rational text `"<n>/<d>"`, at least 0; anything else throws, since it would never pass an instant and the run would step forever) and applies every input stamped by `t`, each at its own stamp, so the run is the same however it is chunked, and as in a replay. In a display run whose frame part waits on a frame not yet logged, an input waits for that frame, which may come first. A display run first logs frames up to `t` on the nominal grid from the last frame (see Run control) |
| `run.advance(t)` | `runUntil` from the log alone, logging no frames: what `replay` runs |
| `run.nextInstant()` | the next instant a part is due at, as a rational, not run; null when none is |
| `run.input(entry)` | adds an outside input, stamped with `entry.T` or the next instant (when none is due yet, as in a display run of frame parts waiting on its next frame: `run.T`, or the first millisecond after it when `run.T` is the last instant run); a stamp at or before the last instant run throws, and one at or before `run.T` applies at once, as `runUntil(run.T)` would. What is knowable when an input is logged is refused then, as a `RunError`, the run unchanged (a log handed to `createRun` as `inputs` is checked the same way, entry by entry): an input naming a part the composition lacks (N009); an `in` input to an input the part lacks, to a value or Draw input, or to one a wire feeds, or a `control` input to any part but the page (N011); an `in` input whose value does not fit the input's seam (N012); a `param` input whose value fits no record that can be in force at its stamp (N008, below); a `param` input changing a param build-time code reads when the run has no `build` option (N010). **The record a param input is judged against** is the one it will apply under, which may not be the part's record when it is logged: a rebuild logged before it and not yet applied changes it. So it is refused at logging only when its value misfits every record that can be in force at its stamp: the part's record now and the record of each rebuild of that part logged before it (a rebuild can fail and keep the record before it, so any of them can be the one). When a build-time param edit of that part is logged before it, the record that edit builds is known only by calling the host's `build`, so nothing is refused at logging. Every param input is judged again as it applies, against the record then in force: one that misfits is not applied, noted as N008 (or N010) with the part keeping its build, the same in a replay. So a log the live run accepted restarts and replays (a rebuild that widened a range, then a value in the new range), an edit queued behind a widening rebuild not yet applied is logged, and no value is ever applied under a record it does not fit. A param the record does not declare is not checked. **What the log may still hold that throws:** a build-time param edit whose value fits but whose `build(part, params)` throws (the host's Program refuses it): the throw comes out of the call that applied it (`runUntil`, `step`, `input`), the input stays logged, its value is in `run.params`, the part keeps its previous build, and the run goes on if called again; a replay of that log throws at the same input. kit/page's host reports it as H004 and offers Resume. Until leaf `GYDKN0` this row said the log never held an input that would throw on replay, and each param input was judged against the part's record when it was logged, so the log of a widening rebuild then a value in the new range could not be restarted (N008), and an input naming no part, or a build-time edit with no `build`, was logged and threw when applied |
| `run.composed` | the composed record in force: each part's record now and each wire's conversions as last planned (a rebuild plans them again: "Re-planning on a rebuild", below); `pageView` reads it |
| `run.params(part)` | a part's params as its Kernels read `$` now, frozen: the declared values, then every param input applied up to `run.T` (an input stamped at the next instant shows once that instant has run). It follows rewinds, restores and rebuilds, so a host reads it rather than keeping its own copy of what it set |
| `run.output(part, output)` | a value output as a wire from it would read it, before conversion: the part's compiled output on its committed state and params (null when its init failed). A Draw or Event output, or a name the part lacks, throws a plain `Error` naming the value outputs |
| `run.tapped(handle)` | the records a tapped Event output pushed (`taps`), `[{ T, record }]` in push order, `T` in seconds, each record a frozen copy; kept with the checkpoints, so a rewind drops what came after its target. Not in the state hashes. An output that is not tapped throws |
| `run.state(part)`, `run.snapshot(part)` | a part's state (null if its init failed); `{ state, revision, T, draws? }`, T the instant it was committed (null: init's), `draws` its Draw lists by port when it has Draw outputs. For a layer (below), state is null and its snapshot `{ state: null, revision: 1, T, draws: { view } }`, `view` its list now and T the latest instant a producer under it committed at |
| `run.T`, `run.seconds` | the time the run has reached |
| `run.catchUp`, `run.lastFrame`, `run.framed` | the catch-up cap (a rational); the last frame at or before `run.T` (a display run starts at a frame at T = 0); whether a running part steps on frames (what the driver reads) |
| `run.revision`, `run.key(part)`, `run.compositionKey` | the composition's revision (bumps when a part's does); a part's content key; the composition's ([kit/build](../build/README.md)) |
| `run.log` | `{ header: { name, seed, frames, catchUp, params }, inputs }`: the input log as data, each `T` as rational text; a param wire's input carries `wire` (below) |
| `run.record()` | `{ log, hashes, builds, T }`: what `replay` compares, and the T the run reached (a replay runs to it, so it applies the inputs the run applied after its last instant) |
| `run.why(part?, since?)` | the [why text](../build/README.md) for that part's builds (every part's when omitted) at or after `since` (seconds, a rational or its text), from the run's own build events and input log: `"why cave: 1 rebuild in the run log; cave@2 now\n\nbuild cave@2 after instant …"`. A function of the log and the events, so a replay gives the same text. A `part` the composition lacks throws a plain `Error` naming the parts |
| `run.hashes` | one `{ T, hash, parts: { name: hash } }` per instant (a fast hash of each state, not a content key) |
| `run.builds`, `run.diagnostics` | the build events ([kit/build](../build/README.md)); every N diagnostic, `{ code, severity, message, part?, T, revision? }` |
| `run.stats()` | `{ dropped: { "<wire>": n }, stopped: { "<wire>": n }, overflow: { "<wire>": n }, slowdowns: [{ from, to, wall, workbench, ratio }] }`: records a `keepLast` input dropped; records sent to a stopped part, dropped; records a wire's overflow policy dropped |
| `run.rewind(t)`, `run.checkpoints` | back to `t` from the nearest checkpoint, replaying forward; inputs stamped after `t` are dropped (a rewind is a branch) |
| `createDriver(run)` | the real-time driver: `frame(wallSeconds)`, `pause()`, `resume()`, `step()`, `paused`; its cap is the run's `catchUp` (passing the driver its own throws) |
| `replay(composed, options, record)` | runs the record's log again: `{ ok, diagnostics, run }`, N005 at the first instant whose state hash differs (naming the parts), or when the build events differ |
| `carry(value, wire)`, `slowdowns(entries)`, `RUN_CODES`, `RunError`, `INPUT_KINDS` | |

**Options.** `runtimes` (matched to parts by Dialect name; required), `packages` (`[{ name, content }]`: each package's content key from kit/package, for the parts' keys), `params` (`{ part: { name: value } }`, else each param's declared value), `inputs` (an input log), `seed` (0), `dev` (true), `frames` (`"nominal"`, or `"display"` under the real-time driver), `catchUp` (seconds, default 1/15), `checkpointEvery` (seconds above 0, default 1), `taps` (Event outputs to keep, `"<part>.out.<output>"`; see "The `in` input, taps and outputs"), `build(part, params)` (the host's rebuild of a part whose build-time param changed: it runs the part's Program again and returns the record; one that throws throws out of the run call that applied the edit, as `run.input` says).

## What a step is handed

`init(record, ctx)` and `step(state, ctx)` are the package's ([kit/define](../define/README.md#runtimes-defineruntime)). `ctx` is below; `init`'s holds only `part`, `revision`, `record`, `kernels`, `rng`, `params` and `globals`.

> **Corrected 2026-11-26 (M4 trial, leaf `IhJ35P`):** this table listed `T` and `dt` without "step only", so an author read `ctx.T` in `init`, got undefined, and the part stopped (N002).


| Key | What |
|---|---|
| `part`, `revision`, `record` | the part's name (its identity), its revision, its built record (read-only) |
| `T`, `dt` | (step only: `init` gets neither, so a state that needs a start time takes it from the first step) the instant in seconds, and the step's length: a tick part's period, a frame part's time since its last frame (0 at its first), 0 for a demand part |
| `inputs` | (step only) each value input, converted (a default when unwired); each Event input's records since the part's last step, converted, in order, each with a read-only `$T` (below); `$rev` the revision of the producer snapshot each input read (null unwired; 1 for a layer, which has no snapshot of its own) |
| `kernels` | the Program's compiled lambdas by id, `<instance>.<slot>` (with `#<n>` unless the slot is `once`: the stable id), the part's own (the root instance is the part) by slot name too (`kernels.<slot>` is `kernels["<part>.<slot>"]`), and a call whose slot declares a name by `<instance>.<slot>.<name>` too, the same function as its positional id (ruling 1, 2026-11-26; a call with no name has only its id); the aliases are not enumerable, so `Object.keys` lists ids |
| `rng` | the part's seeded stream: `rng()` in [0, 1) |
| `events` | an empty list per Event output (step only): push records into `ctx.events.picked` |
| `globals` | what the Kernels' global names read in this step: the params, under the Dialect's params name (`params.name`, `$` by default; fields names them `u`), the inputs object (the value inputs); set any other the Dialect declares before calling a Kernel that reads it (an Event record's name, `ctx.globals.<name> = <record>`; any object the Dialect shares between lambdas). An Event record's name reads as null in a Kernel called while it is unset or null (ruling 6, 2026-11-26), so set `ctx.globals.<name> = null` before calling a listed slot without a record; its lambdas test `<name> != null` (kit/define, "An Event input's record"). Any other global read unset throws (N004) |
| `params` | the params, as `$`: the only place a runtime reads a param's value (never `record.params.<name>.value`, which the content key does not see; kit/define) |
| `files` | the package's data files, by the name the Dialect gives each under `files` (kit/package's decoded `data`: a CSV's rows, a JSON's value, a text file's text), frozen; `{}` for a package with none or a run given no packages (declared Controls, ruling 5, 2026-11-27). They are read once, at `createRun`, from the packages it was given: a `rebuild` input whose `package` names new content restarts the part with the files it started with, since the input carries only the content key and the log no files (a known limit, leaf `FtbfNP`: delivering new files would change the log's format; until then a host that swaps a package's data starts a new run) |

**Draw lists** ([`draw.js`](draw.js); the draw-list draft, as ruled 2026-11-26). After a part's init and each step, each of its Draw outputs is built from the state it returned, with its record, its params and its inputs (value inputs and Draw inputs, through the inputs global; init sees the defaults, so a Draw input is `[]`), by [kit/draw](../draw/README.md)'s `runDraw`, through its builder layers' compiled Kernels: `compilePart` emits each layer kit/define lowered (`compiled.draws[<port>]`: the Program's max and one function per layer, their text in `sources` by `ports.out.<port>.<layer>`), with the Dialect's globals bound as every Kernel's are, so `$` and the inputs global read `globals.current`, which the part sets before building them. Nothing is set on the global object. Every Dialect global a Kernel reads is the run's value, through `globals.current`, except the page globals (kit/define's `PAGE_GLOBALS`, an explicit list, today only `Math`), which it reads from the page; until leaf `9t99go` the test was `name in globalThis`, so in a browser a Dialect global named `status`, `screen`, `name`, `top`, `origin` or `event` read the window's, not the run's. A builder that fails stops the part with its J code (J010, J020–J022), as N002 does. A part's lists are committed with its state (`part.draws`), and the View a wire reads holds the snapshot's lists beside its state, so a delayed wire, reading the snapshot as its instant began, reads that snapshot's lists, even from a step that returned the very state object it was handed, and two parts that commit one object keep their own (review F1; until then the lists were kept by state object alone). A list is a pure function of the committed state, the record, the params and the inputs, so a rewind builds them again: a checkpoint copies the inputs and the params the part's lists were last built with (`drawValues`, `drawParams`, set as the state is committed), and each restored part's lists are rebuilt from its restored state (`redraw`). The params are the ones as they stood at that commit, not the part's current ones: a param input, or a rebuild that keeps the key, changes `$` without building the lists again, so a straight run keeps showing the old lists until the part next steps, and so does a rewind into that gap. A part that stopped keeps its last commit's lists, in a straight run and after a rewind alike; only a part whose init failed has none. Carrying the params, not the lists, adds one shared reference per part to a checkpoint and keeps the lists a function of what it holds (a checkpoint whose states were read back as equal copies still redraws them). A run rewound to any checkpoint then run on gives the straight run's state hashes, a consumer whose state depends on a Draw input included, through a stopped producer and a param change between steps too (leaves `WNeULS` and `9t99go`, `test/draw-restore.test.js`; until `9t99go`, a stopped part redrew none, and a redraw read the current params). A Draw wire converts the list op by op into the consumer's frame, sizing unsized images and tiles from the producer's declared images. `pageView(run, composed, runtimes, part?)` gives what a renderer needs: `{ part, port, list, images, box, check }`, the shown part's Draw output (the composed record's `view`; a layer's `view`, "Layers" below), every part's images by their carried names, and the box of the output's frame (its extent for the record in force, which a rebuild changes; for a layer, its bottom producer's grown to the union of its other inputs' boxes, each placed by its wire's conversion, so it need not start at the origin); it reads the records and conversions in force from `run.composed` ("Re-planning on a rebuild", below; until leaf `QqirvU` it read the composed record's, so the box stayed at the first build's extent); when the composition was built with a renderer profile (the composed record's `profile`, which kit/compose keeps from `build(options)`), `check` is kit/draw's draw-time `checkDraw` of the list (J040–J044: what composition cannot count), else null. The list is never trimmed to pass it; the page shows or reports the diagnostics ([kit/page](../page/README.md) reports a failed check as a page diagnostic). Until leaf `hca0YM` the record did not carry the profile and a caller passed it again as `{ profile }`; that parameter is gone.

## Invariants

- **One workbench time, exact.** Instants are rationals: a tick part's are multiples of its period, so 1/8 and 1/30 meet exactly at 1/2. Headless frame parts step at multiples of 1/60; under the driver at the logged frames. Demand parts make no instants of their own.
- **The page part** (Ben's ruling 5, 2026-11-26; [kit/compose](../compose/README.md), "The page"). A composed `page` part is never stepped or hashed. A `control` input addressed to the part `page`, `{ kind: "control", T, part: "page", name: "<control>", value }`, is copied and checked against the declared Control's seam the composed page lists (`controls`) when it is logged (N013 for a Control the page lacks, N012 for a value that does not fit; a later change to the host's object changes nothing), and applied at its stamp like any input: one record, converted and stamped (`$T` its stamp), onto each wire from `page.out.<control>`, so a consumer takes it at its first step at or after the stamp. **Every press and release arrives** (Ben, 2026-11-26: "we need tap and release"): each page input is its own record on each wire from that control, in log order, each `$T` its own stamp, so a tap whose press and release both land between two steps of the consumer reaches that step as both records, the press first. Compose sized the wire for each Control's `perFrame` records a display frame (declared Controls, 2026-11-27; until then `PAGE_CHANGES_PER_FRAME`, 2 for every control); the host does not enforce that, so a person (or a stalled frame that gathers many key events into one instant) can exceed it. Past the consumer's max, the wire's overflow policy trims what the step takes (`stats().overflow`, N001). **A page wire with no policy folds** (Ben, 2026-11-26: a person is the one sender no party controls, so a page wire past its size never stops its part): with max m and k > m records ready, the step takes the first m-1 in order and then the latest as the m-th, each with its own `$T`; the k-m folded between are counted in `stats().overflow` and noted as N001 once per wire (again after a rebuild restarts the consumer). With m = 1 the step takes only the latest. This is a **state** Control's fold: every record is the Control's whole state (every button, a number's value), so the latest record is the state now: the final release always arrives, and no button sticks down. A glue's own `overflow` on the wire still wins, and every other wire is unchanged (a reliable wire past its max is still N002). The fold happens at delivery, from the queue alone, so the log keeps every input as given and a replay, a chunked run and a rewind deliver the same records as the straight run (`test/page-inputs.test.js`). **Reversed 2026-11-26:** from `3bfd8ee` until this change a page wire with no policy had its consumer's step refused past the max (N002: the part stopped, and its waiting records were counted in `stats().stopped`), so one burst of key events stopped the part for good. **Reversed 2026-11-26:** from `ada0afe` until this change a page wire held only the latest value per control until its consumer took it, replacing a record not yet taken, so a tap between two steps arrived as its release alone. That was wrong for taps (Ben's ruling, in [the seams draft](../../project/2026-11-25-seams-draft.md), last block). A control nothing is wired to is logged and goes nowhere. These apply only when the composition has the built-in page part: a page input to a composition with neither is refused when it is logged, as an input naming an unknown part is (N009), and a control input to a user part that is itself named `page` is refused (N011). Page inputs are in the log, so a replay presses the same. A headless run's page sends only its scripted inputs; under the real-time driver the host calls `run.input({ kind: "control", part: "page", name, value })` when the person changes a control, stamped at the next instant as any input. A page consumer's `$rev` for that input is 1. **`ctx.controls` is retired** (Ben's ruling 1, 2026-11-27: "A smaller and simpler API surface is always better if possible"; until leaf `ceE4ib` a part run without a glue got inputs addressed to it by name there). A part takes a Control as the Event input of its name, fed by a page wire (kit/page's `examplePreset` wires each declared Control to that input by name) or, in a headless run or a test, by an `in` input. A `control` input addressed to any part but the built-in page is refused when logged (N011). A part's held state across a rebuild is its state, which a rebuild restarts: the page sends a record only when a control changes, so a pad held across a rebuild reads as released until the next change (it used to persist in `ctx.controls`). A user part named `page` takes `in` inputs like any part.
- **Delta records carry over** (declared Controls, 2026-11-27). A **delta** Control's page wire (`triggers`: each record a note on or off) is never folded and never dropped: past the consumer's max, the step takes the first max in order and the rest wait for the next steps in the same order, each keeping its own `$T`, so a burst costs latency, never a note. `stats().carried` counts each record that waited (once, however many steps), and the first carried record of a wire notes N001 once. A **keyed** state Control (an `each`) folds per key: of a key's waiting records only its latest is taken, and keys past the max wait. A straight run, a chunked run, a rewind and a replay deliver the same records (`test/controls.test.js`).
- **The pointer input** (`{ kind: "pointer", T, part, output?, value }`; requirement 5). The composed part entry's `pointer` (`{ <Draw output>: "<input>" }`, from its UI) names the Event input a pointer event goes to; a part that takes none is refused when it is logged (N013), and a value that does not fit that input's seam (kit/define's `pointerSeam`) is N012. Its queue is a delta queue: down, up, cancel, wheel and leave are never dropped and carry over past the max, and a run of moves with nothing between them coalesces to each pointer's last (by the record's `pointer`, so two fingers moving in turn each keep their last move; the queue stays in stamp order; `test/pointer.test.js`). **Corrected 2026-11-27** (leaf `udUBOI`): a run of moves coalesced to the last move of any pointer, so the other finger's moves never arrived. kit/page routes the pointer to the part under it.
- **`pageView` names each op's part**: beside `list`, `parts` and `ports` give the part and output that made each op, through a layer's inputs, so the page can route the pointer.
- **Layers** ([`layers.js`](layers.js); [kit/compose](../compose/README.md), "Layers"). A part entry that carries `layer` is never stepped: it needs no runtime, and adds nothing to the log, the state hashes, `stats()` or the checkpoints. Its output, wherever it is read (a wire from it, `pageView`, `snapshot`), is each of its input wires' lists carried as any Draw wire's is (`carry`, so `convertOp` by the planned edge, images sized from every part's declarations) and concatenated bottom first, from the producers as the reader sees them: a delayed wire from a layer reads every producer under it as the instant began. A consumer of a layer steps after every producer under it (wire order, below). `pageView` of a layer gives its list in the box of the stepping producer at its bottom (down through a layer at the bottom), grown to hold each other input's box placed by its wire's conversion (Ben's ruling, 2026-11-27: a picture anchored outside the bottom one, a label under it, is on the page; an input whose frame has no extent adds nothing, and a bottom frame with none gives no box). A record whose layer has fewer than two inputs, an input with no wire or several, an input from anything but a Draw output of a stepping part or another layer's `view`, an output on two inputs, a `layer.inputs`, `max` or `frame` that disagrees with its wires, a delay or rename on a wire into it, a wire from a layer port but `view`, or layers that feed each other, is refused at `createRun` (N007): never drawn empty. A producer whose init failed has no list, so the layer draws the others' (its N004 says why).
- **Wire order within an instant.** The parts due step producer before consumer along undelayed wires (a wire from a layer, after every producer under it); ties go by `.part` order. A consumer reads each value input from its producer's latest snapshot, so a same-instant producer has already committed. A delayed wire reads the snapshot as the instant began, and takes only Events stamped before it. kit/compose refuses an undelayed cycle (S115).
- **Events exactly once, in order.** Each Event wire keeps a queue of records stamped with T. **Each record carries `$T`** (ruling 3, 2026-11-26): its producer's instant, in seconds as `ctx.T` is, set when the record crosses the wire, on a copy: the run copies the record, stamps it, then freezes the copy, so an object a producer or the host handed in (frozen, kept in state, or pushed again) is never changed, and `$T` is the same in dev and non-dev runs. It is read-only (the record is frozen, so writing it throws, N003 in a development run and N004 otherwise) and not enumerable, so a record's keys, a spread and its JSON are its fields; a replay stamps the same. A step takes every record ready for it, in stamp order, then push order. A reliable wire's bound was checked at composition (S116); a `{ keepLast: n }` input keeps the newest n, and its drops are counted in `stats().dropped` and noted once per wire as N001. **A stopped part takes no Events** (Ben, 2026-11-26): the records waiting for it when it stops, and those sent to it while it is stopped, are dropped, counted in `stats().stopped` and noted as N001 (a warning) once per wire for each stop: a restart clears the note (ruling R3); "reliable" promises delivery to a running part. A record handed to the step that stopped it was delivered. A step that would take more records from an Event input than its runtime declares (a hand-written display log whose frames are farther apart than the cap, say) is refused: the part stops with N002 and none are taken (a page wire folds instead: "The page part" above). **A wire with an overflow policy** (ruling 7, 2026-11-26) is never refused this way and is not sized at `createRun` (S116 is compose's warning): each step takes at most the runtime's max of the ready records, the newest (`keepLast`) or the first (`keepFirst`), and drops the rest, counted in `stats().overflow` and noted as N001 once per wire, again after a rebuild restarts the consumer, as a stopped part's drops are. Records cross wires in [`delivery.js`](delivery.js).
- **Crossing a wire:** the rename first (a record's fields, or each item's in a list of records; a conversion and a dropped path name the consumer's field), then the producer's fields the consumer does not take are dropped by path (`keep`, `inner.x`, `pts[].x`, a list's `[].k`), then each tagged leaf converts: a point by scale and offset (a `point1` is one number), a vector by scale, a quantity by its one magnitude; then each field the plan fills (`fill`: a consumer default the producer's record lacks) and each wire constant (`set`: the glue's literal) is given, in a copy per record, replacing whatever a runtime pushed under that name: the plan decided statically that the producer's seam lacks the field.
- **A demand part** steps at the first instant, after a rebuild, when an Event is ready for it, or when a value input's converted value differs from what it last read.
- **Steps are checked.** After init and every step the state is checked with the Dialect's `checkState(state, record)`, against the part's Program's state (the Dialect's, with the fields the Program declares added to its extensible struct; [kit/define](../define/README.md), "Per-Program state"), and the Event counts against the runtime's maxes, pushed and taken (N002). A field in the extensible struct that the Program does not declare is N003 in every run: the step kept memory outside its state (the message lists any other misfit of the same state beside it). In a development run (the default) every state is frozen, and each step runs twice on the same state and inputs, which must agree (N003: a module-level variable, `Math.random`, a clock). A throw is N004. Any of these stops the part; the others run on with its last snapshot.
- **A run is a pure function** of the composed record, the params and the input log. Inputs (`control`, `in`, `param`, `rebuild`, `frame`) take effect at their own stamps, in log order, so a part reads them at its first step at or after the stamp; a param wire's input, which a run makes, applies right after the instant it is stamped with (below). Replay compares every instant's state hashes (N005).
- **Rebuilds land between instants.** A `rebuild` input carries the new record (a glue edit or package swap the host built; `package: { content }` for a new package key, `trigger` for the event); a `param` input whose param build-time code read (`record.reads`) calls `options.build` (a run with no `build` refuses such an input when it is logged, N010). The revision bumps only when the part's content key changes; init then runs again on the new record, and the Event queues are kept (a part a rebuild restarts has none: they were dropped while it was stopped). A rebuild that fails (it does not lower, its clock does not read, its re-plan fails, or its init throws or returns a state that does not fit) keeps the previous revision running: init runs on a trial copy, and the build event is not ok and carries the diagnostics. **A rebuild takes effect at its own stamp** (ruling R2, 2026-11-26), and its boundary names the last instant run and that stamp: a part it restarts, or whose clock it changes, has its first instant at the first on its clock at or after the stamp, whatever other parts are in the composition (with a 1 s ticker beside it, a 1/8 s part restarted at 1.01 steps at 9/8). No instant runs before an input already applied, and the run is the same however `runUntil` is chunked and in a replay. Each writes a build event ([kit/build](../build/README.md)). A param's value is not in the content key (kit/build), so a param change that builds the same record keeps the revision. A rebuild's record gives `$` its declared values for the params nothing has set (`options.params` and the log's param inputs set them), whether or not the key changed: a new default reaches `$`, and so does a new param.
- **Re-planning on a rebuild** ([`replan.js`](replan.js); Ben's ruling, 2026-11-27; [kit/compose](../compose/README.md), "An anchored edge"). A wire's conversions start as the composed record planned them. A rebuild that changes a part's content key plans every wire's again before init runs, with kit/compose's `replan`: the frame graph from the parts' frames, each Dialect's `edges(record)` for the records now in force (the rebuilt part's new one), then the composed record's `frames` (the glue's edges) in order, each `"fit"` or anchored edge computed from the extents now in force. A plan that fails (two paths that now disagree, S253; a path the rebuild removed, S251; a quantity's path that no longer scales its axes alike, S254; an extent gone, S256) fails the rebuild: the previous revision runs on with its conversions, and the build event carries the S diagnostic. A plan that succeeds applies with the rebuild, at its stamp, to every wire and every layer input: a value or Draw wire read after it, and an Event record sent after it, convert by the new edges, while a record already queued keeps the conversion it got when it crossed (records convert as they are pushed, [`delivery.js`](delivery.js)). Its build event names each edge that moved, `edges: [{ from, to, before, after }]` (frames as `<part>.<frame>`; `null` for an edge that appeared or went), and the why text prints them. The plan is a function of the records in force, so a replay plans the same; a checkpoint keeps it, so a rewind past a rebuild restores the earlier plan with the earlier record. `run.composed` is the composed record in force: each part's record now and each wire's conversions and glue edge as last planned (the record `createRun` was given is never changed). A rebuild that keeps the key changes no record, so it plans nothing. Until leaf `QqirvU` (issue `Wd9nH5`) every conversion was copied once at `createRun`, so a rebuild that changed an extent left "fit" edges, a Dialect's `edges(record)` and the page box at their first numbers. **Corrected 2026-11-27 (leaf `EggIAM`):** `pageView`'s box followed from then, but kit/page sized, cleared and translated its canvas by the box at creation until `EggIAM`, so a picture that grew on its min side was drawn off the canvas.
- **A param wire** (`.wire(<part>.out.<port>, <part>.param.<name>)`, [kit/compose](../compose/README.md); the seams draft's ruling, 2026-11-26, leaf `x3iG6D`) is applied between instants: after each instant, its producer's output is read, and when its value differs (canonical comparison) from what the param holds then, a `param` input is logged, **stamped with the instant that made it**, and applied right after that instant, ahead of every later one (R2), as any param input is: it rebuilds the part when build-time code reads the param (the build event's boundary is `{ after: T, before: T }`, which the why text reads as `right after instant T`), and replay and `run.why` read it from the log. The input carries `wire: "<part>.out.<port>"`, the output it came from, and that field is what tells a wire's input from an outside one: before the instant `T`, the run applies the log's inputs stamped `T` up to the first wire input stamped `T`, and that one and the log after it wait until the instant has run. A run from a log (a replay, or a run given `inputs`) applies a logged wire input once, since the wire adds none when the log already holds one from that wire at that stamp, and carries on applying the wire live past the log's end, so a wire's input is made exactly once per change, live, replayed or carried on. A rewind keeps the wire inputs of the instants it runs again. A value that does not fit the param's declaration (its type, finite, `min..max`, `options`) is not applied: N008, once per value. The param follows the output: a host's param input to a wired param holds until the next instant has run, when the wire sets the output's value again (each such input rebuilds the part).
  - **Why the stamp is the producing instant** (leaf `DJZ2z2`, the review of `5db1d27`). The stamp must be a function of the instant that made the input alone, and land before every later instant, in nominal and display runs alike. Until this leaf it was the next instant, which in a display run depends on which frames are logged yet (a chunked run, a whole run and a replay stamped one change differently, and a replay applied it twice: N005), and a host input at that stamp hid the wire's logged input from the "already logged" test (N005 again). The producing instant's own millisecond plus one (`afterMs`) is no sounder: two instants can fall inside one millisecond (a tick finer than 1 ms, or a 1/60 s tick beside a display frame on the millisecond, 16 ms and 16.67 ms), and the wire's input would then land after the later one. The instant itself, applied right after it, needs no bound on how close instants are, and depends on nothing logged later.
  - **A host input and a wire input on one param at one stamp: the log order decides.** A host's input stamped at an instant `T` is logged before that instant runs (`run.input` refuses a stamp at or before the last instant run), so it applies before the instant's steps and the wire's input, logged after the instant, overrides it. In a log that holds a host input after a wire's input at one stamp, the host's applies after the wire's, right after the instant.
- **Real time slows instead of dropping.** The driver advances T by each display frame's wall time, and no logged frame covers more than the run's `catchUp` since the frame before it: the window S116 sized the queues for. A display run starts at a frame at T = 0 (as a headless one does), so the first frame's window is half-open too. The driver's frames are kept to the millisecond (a capped one lands exactly on the cap; runUntil's lie on the nominal grid, below), and one closer than 1/240 s to the last frame is merged into the next, whose cap still counts from the last logged frame. Each frame is logged, a capped one with its wall time, so replay steps frame parts at the same T. A run of capped frames is one N001, written at its first capped frame and rewritten at each one after ("has run at 0.13× for 30 s of wall time …, and has not caught up"), so a run that never catches up still says so; the first frame that is not capped closes it ("ran at 0.13× for 2 s of wall time"). A rewind keeps it as it stood then.
- **Run control.** `driver.step()` runs the next instant, paused or not; when a part steps on frames, a step goes at most one nominal frame (1/60 s) past the last frame (when T already stands that far past it, as after a rewind between capped frames, to the cap past the last frame instead) and logs a frame when it gets there, so frame parts advance while paused and the window holds. Anything else that moves T resets the driver's place. `runUntil` on a display run logs frames up to its target on the nominal grid from the last frame (last + k/60 at or before the target; none at a target off the grid: ruling R1), whether or not a frame part runs, as the driver logs every display frame. When T stands past the last frame (after a rewind), the first is never past the catch-up cap from it: if the next grid point is, the first frame is the cap, and the grid goes on from there. So chunking changes nothing (except where a hand-written log already holds frames ahead of T: the grid starts from the last of them at or before the target, so where runUntil is cut decides which), frame parts step through a skip ahead as they would headless, a part restarted mid-run steps within the cap, and the driver's next frame counts from the run's T. When T moved without frames (`advance` from the log alone), the driver's window counts from T, so no frame is capped that wall time did not slow. A rewind logs none: its next frame counts from the last frame at or before T, which is within the cap of it. A frame costs the same at any length of run: frames are found by binary search.
- **Checkpoints** every `checkpointEvery` seconds of T hold every part's state (shared, since state is immutable), stream, build and queues; rewind restores the nearest and replays.

## Codes

N is kit/run's letter, reserved in kit/define (a Dialect's own codes may not use it). The clocks draft named these R001–R006; Ben ruled them N on 2026-11-26 (leaf `p3OBui`), since kit/lir reports R001–R006 and the particles packages use R as their own letter.

| Code | When |
|---|---|
| N001 | the run fell behind wall time and T slowed (a warning, with how long and how much, while it lasts and when it ends); an input's `keepLast` dropped records (counted); records sent to a stopped part were dropped (counted in `stats().stopped`); a wire's overflow policy, or a page wire's fold into the latest held state, dropped records (counted in `stats().overflow`) |
| N002 | a step returned a state that does not fit the Dialect's `state` (the paths), pushed more Events than its runtime declares, or would take more than it declares from an Event input; also an init's state |
| N003 | a step or init kept memory outside its state: a field in the extensible struct the Program does not declare (any run), or, in a development run, a step that changed the state it was handed or gave another result the second time |
| N004 | a step or init threw (also a part whose lowering throws) |
| N005 | a replay diverged: a state hash differs at an instant, or the build events differ |
| N006 | a runtime's `clock(record)` is not one (refused at `createRun`; in a rebuild, the build event fails) |
| N007 | a composed record kit/compose would not have built, refused at `createRun`, so only a hand-edited record reaches it: the record has no `frames` list (compose writes one, empty when the glue relates no frames; a rebuild plans the glue's edges again from it), a conversion has no `fromId` and `toId` (the frame ids compose records, which a rebuild re-plans by), a wire's `overflow` is neither `"keepLast"` nor `"keepFirst"` (compose's S102), or a layer has fewer than two inputs, an input with no wire or several, an input from anything but a Draw output of a part in the run, an output on two inputs, a `layer.inputs`/`max`/`frame` that disagrees with its wires (`max` is the sum of its inputs' built maxes, a layer input counting as that layer's max), a delay or rename on a wire into a layer, a wire from a layer port but `view`, or layers feed each other (compose builds every layer from two or more Draw outputs) |
| N008 | a param's value does not fit its declaration (its type, finite, `min..max`, `options`): a param wire's is not set and the part keeps its build, noted once per value; a param input's is refused by `run.input` (a `RunError`, the run unchanged) when it fits no record that can be in force at its stamp, and otherwise, when the record in force as it applies refuses it, not applied (noted, the part keeps its build) |
| N009 | an input names a part the composition does not have: refused when it is logged (a `RunError`, the run unchanged) |
| N010 | a param input changes a param build-time code reads, and the run has no `build(part, params)`: refused when it is logged (a `RunError`); not applied (noted) when only a rebuild logged before it made the param build-time |
| N011 | an `in` input addressed to an input the part does not have, to a value or Draw input, or to an Event input a wire feeds; or a `control` input addressed to any part but the built-in page: refused when logged (a `RunError`), as N009 is |
| N012 | an `in` input whose value does not fit the input's seam: refused when logged (a `RunError`) |

## The `in` input, taps and outputs

Built for package tests ([kit/package](../package/README.md), "Tests", which holds the reasons) and for headless runs; leaf `ceE4ib`.

- **`{ kind: "in", T, part: "<part>", name: "<input>", value: <record> }`**: one record on the part's Event input `<input>` that nothing is wired to, as if a wire had delivered it at `T`. Each Event input no wire feeds has a queue of its own, shaped as a wire's (`outside.js`; its text in `stats()` and the diagnostics is `in → <part>.in.<input>`), so delivery, intake, stopping, the checkpoints and the counts treat it as one. The record is copied and checked against the input's seam when it is logged (kit/seam's `valueProblem`: N012), the log keeping it as given; when it is delivered each missing field that has a default is filled (as a wire's `fill`), and it is stamped (`$T` is `T`) and frozen. No conversion: the record is already in the input's seam and frame. The input's `delivery` applies as on a wire (`{ keepLast: n }` trims, counted in `stats().dropped`, N001); a stopped part takes none (`stats().stopped`, N001); a step takes the ready records in stamp order, then log order, and one that would take more than the runtime's `events.in.<input>` is refused, the part stopping with N002, as on a reliable wire (S116 does not apply: there is no wire to size). `$rev` for the input is 1, as for a page input. Refused when logged (`RunError`, the run unchanged): a part or input the composition lacks (N009, N011), a value or Draw input (N011; later: a value input takes the latest value at its stamp), an Event input a wire feeds (N011: two senders on one queue would interleave records sized for one), a record that does not fit (N012). A rewind, a chunked run and a replay deliver what the straight run did (`test/in-input.test.js`).
- **`taps: ["<part>.out.<output>", …]`**, a `createRun` option, and **`run.tapped("<part>.out.<output>")`** → `[{ T, record }]`. A handle that is not an Event output of a part throws at `createRun`, naming the Event outputs.
- **`run.output("<part>", "<output>")`**: above.

## Not built

Sampling modes and `lerp` (latest only), Workers, a content-keyed cache, swapping a package's runtime code in a rebuild (a rebuild changes the record and the package key, with the runtime it started with), re-sizing queues after a rebuild changes a clock (the run-time intake check, N002, still refuses a step past its max), a workbench of demand parts only (nothing makes an instant), a bound on what a long run keeps (the input log, the per-instant hashes and the checkpoints grow with it; a replay and a rewind read them).
